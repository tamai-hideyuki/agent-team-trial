# テスト可能性レビュー

担当観点: 実行結果が「いつ実行するか」「どの環境で実行するか」に依存する箇所と、その固定・注入方法がDESIGN.mdに書かれているか。

検索方法: `grep -n -iE "モック|注入|フリーズ|freeze|固定|シード|seed|環境変数|TODO_HOME|monkeypatch|inject|mock|時刻を|クロック|clock" DESIGN.md` → ヒットなし。`grep -n -iE "ポート|port|動的" DESIGN.md` → 33行目・275行目のみ(いずれも仕様定義で、テスト用の動的割り当てには触れていない)。9章(280〜286行目)を全文確認。

## 指摘一覧

### 1. 現在時刻依存 — `created_at`/`completed_at`のタイムスタンプ生成
- 該当箇所: 3章 データモデル(117〜118行目) `created_at`/`completed_at` はISO 8601タイムスタンプ。
- 問題: 生成元(`datetime.now()`相当)を注入可能にする設計(時刻プロバイダを外から渡す/環境変数で固定するなど)が書かれていない。
- 確認結果: 9章の「単体テスト」(282行目)にストレージ層は挙げられているが、タイムスタンプを固定してアサートする方法の記載なし。「モック」「注入」「固定」等のキーワードで検索したがヒットなし。
- 影響: `add`のタイムスタンプ値そのものをテストで検証しようとすると、実行時刻に依存して毎回異なる値になり、決定的なアサーションが書けない。

### 2. 現在時刻依存 — 期限切れ判定(5.9節)
- 該当箇所: 179行目「期限が過去日の場合、括弧内に『期限切れ』という文字列を追記する」
- 問題: 「過去日」判定は実行時の現在日付に依存する。テストでは「今日から見て過去の日付」を動的に計算しないと決定的なテストが書けないが、DESIGN.mdにはその方法(現在日付を注入可能にする、テスト内で相対日付を計算する、等)の記載がない。
- 確認結果: 9章のCLI結合テスト(283行目)に「期限切れ」判定のテストへの言及自体がない。使用例(101〜102行目)は日付形式エラーのみで、期限切れ表示のテストケース例も無い。
- 影響: テストコードが実行日に依存した固定日付(例: "2026-01-01"を過去日として決め打ち)を使うと、将来的にテストの意味が変わる・壊れる可能性がある。設計書に「テスト実行時の現在日付を基準に相対的な期限を計算してテストする」等の指針がない。

### 3. 乱数依存 — CSRFトークン生成(8.3節)
- 該当箇所: 277行目「サーバ起動時にランダムなトークンを生成し」
- 問題: トークン生成のシード固定・注入方法(テスト時に既知の値を使えるようにする、または生成関数を差し替え可能にする)の記載がない。
- 確認結果: 9章の「サーバ結合テスト」(285行目)は「`X-Todo-Token` 欠落・不一致時の拒否」を確認するとあるが、正しいトークンをテストコードがどうやって取得するか(サーバ起動時にトークンをファイル/APIで取得できるのか、ログに出すのか等)の記載がない。「シード」「seed」で検索してもヒットなし。
- 影響: テストが正しいトークンで状態変更系リクエストを送る正常系テストを書けるかどうかが設計上不明。トークンをテストから取得する経路(例: 起動時に標準出力に出す、`/api/token`のようなテスト専用エンドポイント、起動オプションで固定値を注入できる等)が必要。

### 4. 環境依存 — ポート番号(`todo serve --port`)
- 該当箇所: 33行目 `todo serve [--port 8765]`
- 問題: デフォルトポート固定(8765)のみで、テスト実行時に他のテスト・他プロセスとのポート衝突を避ける方法(ポート0を指定してOSにランダム割り当てさせる、テストごとに空きポートを探す等)の記載がない。
- 確認結果: 9章の「サーバ結合テスト」(285行目)・「同時実行テスト」(286行目)は`todo serve`を起動する前提だが、使用するポートについての言及なし。「ポート」で検索した2件(33行目・275行目)はいずれも動的割り当てに触れていない。
- 影響: CI等で複数テストを並行実行する場合、固定ポート8765の奪い合いでテストが不安定(flaky)になるリスクがある。

### 5. 環境依存 — 保存場所(`~/.todo/todo.json`のホームディレクトリ依存)
- 該当箇所: 139行目「保存場所: `~/.todo/todo.json`」
- 問題: 保存先パスをテスト用に差し替える方法(環境変数でベースディレクトリを指定可能にする、CLIオプションで指定可能にする等)の記載がない。
- 確認結果: 「環境変数」「TODO_HOME」で検索してもヒットなし。9章のどのテスト項目(282〜286行目)にも、テスト用に隔離されたストレージパスを使う方法への言及がない。
- 影響: このままだと単体テスト・結合テストが実行環境の実ホームディレクトリ(`~/.todo/todo.json`)を直接読み書きすることになり、開発者の実データを破壊するリスクがある。テスト分離の観点で重大。

### 6. 環境依存 — `threading.Lock`とstale lock判定の時間(4章、10秒)
- 該当箇所: 159行目「取得時刻から一定時間(例: 10秒)以上経過している場合は、そのロックを破棄」
- 問題: この10秒という値をテストで待つと1テストあたり10秒以上かかり非現実的。閾値を注入可能にする(設定可能にする、テスト時は短縮する)方法の記載がない。
- 確認結果: 9章の単体テストに「stale lock判定」が対象として明記されている(282行目)が、10秒という実時間を短縮してテストする方法(例: 閾値をパラメータ化する、モック時刻を使う)への言及がない。
- 影響: stale lock判定のテストが書けない、または書くと非常に遅いテストになる。

### 7. 環境依存 — OSのプロセス存在確認(PIDチェック)
- 該当箇所: 159行目「記録されたPIDが現在存在しない」
- 問題: プロセス存在確認(おそらく`os.kill(pid, 0)`相当)をテストでどう固定・モックするかの記載がない。存在しないPIDをテストで安定して用意する方法(例: 十分大きい値を使う、モック可能にする)への言及がない。
- 確認結果: 9章にPID存在確認のテスト方法への言及なし。
- 影響: 「PIDが存在しない」ケースのテストが環境(OSのPID割り当て状況)に依存し、決定的でない可能性がある。

## まとめ
9章(テスト計画)には対象領域の列挙はあるが、上記7点すべてに共通して「テストで結果を決定的にするための固定・注入方法」の記載が欠けている。特に5番(保存場所のホームディレクトリ依存)は実データ破壊リスクがあるため優先度が高い。
